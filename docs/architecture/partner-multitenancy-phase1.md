# TALVOA — Modelo comercial multi-tenant (Fase 1)

Status: desenvolvimento isolado em branch; **não implantado em produção**.

## Hierarquia

- TALVOA: operadora e proprietária da plataforma; administração e suporte globais.
- SupriTech: parceiro/contratante da TALVOA; administra somente sua carteira de empresas.
- Guerra Implementos: cliente atendido pela SupriTech; ambiente atual de homologação.
- Outros clientes: empresas adicionais da carteira SupriTech, isoladas entre si.
- Portal final: **opt-in por empresa**, habilitado/desabilitado pelo parceiro.

## Esquema proposto (migração futura, não executar diretamente)

```sql
CREATE TABLE partners (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  name VARCHAR(180) NOT NULL,
  active BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

ALTER TABLE companies_v2
  ADD COLUMN partner_id BIGINT NULL REFERENCES partners(id),
  ADD COLUMN customer_portal_enabled BOOLEAN NOT NULL DEFAULT FALSE;

CREATE INDEX ix_companies_v2_partner_id ON companies_v2(partner_id);

CREATE TABLE partner_memberships (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  partner_id BIGINT NOT NULL REFERENCES partners(id),
  user_id BIGINT NOT NULL REFERENCES users_v2(id),
  role VARCHAR(30) NOT NULL CHECK (role IN ('partner_admin', 'partner_operator', 'partner_viewer')),
  active BOOLEAN NOT NULL DEFAULT TRUE,
  UNIQUE(partner_id, user_id)
);
```

A migração real deverá ser idempotente, reversível e testada em staging antes de qualquer aplicação ao Supabase de produção. Não cadastrar SupriTech automaticamente sem confirmação dos dados comerciais.

## Autorização — regras obrigatórias

1. `platform_admin`: administração global TALVOA; ações de suporte auditadas.
2. `partner_admin`: empresas do parceiro, configuração de acesso final e gestão dos Agents da carteira.
3. `partner_operator`: operações e relatórios das empresas do parceiro, sem administração global.
4. `partner_viewer`: consulta apenas às empresas vinculadas.
5. `client`: somente a própria empresa, se `customer_portal_enabled = TRUE`; exceção de bootstrap/legado deve ser planejada explicitamente.
6. Todo endpoint que aceita `company_id` deve validar vínculo ao parceiro no backend, sem confiar no ID enviado pelo frontend.
7. Agents continuam autenticados por credenciais específicas da empresa; nunca herdam privilégios do parceiro.
8. Exportações, relatórios e consultas históricas devem aplicar o mesmo escopo de autorização das telas.
9. Isolamento deve ser coberto por testes negativos (parceiro A não consulta/edita dados do parceiro B).
10. Tokens e credenciais nunca devem aparecer em logs, listagens ou payloads de cliente.

## Compatibilidade com produção

- Manter `companies_v2.id`, `users_v2.company_id`, `printers.company_id`, histórico, tokens e sessões existentes.
- A Guerra permanece no banco Supabase atual, sem recriação ou migração de dados.
- Antes de vincular Guerra a SupriTech, criar/validar entidade parceira e política de acesso.
- Não habilitar automaticamente o portal final.
- Não modificar configurações Render/Neon/Supabase nesta fase.

## Critérios de aceite

- TALVOA vê todos os parceiros e pode auditar suporte.
- SupriTech vê apenas empresas da própria carteira e pode instalar/vincular Agents a elas.
- Guerra não vê outra empresa; seu portal pode ser ligado/desligado pela SupriTech.
- O usuário não consegue contornar permissões alterando URLs, IDs ou payloads.
- Relatórios da Guerra e coleta atual continuam operacionais.
- Testes de autorização, migração, rollback e regressão passam em staging.
